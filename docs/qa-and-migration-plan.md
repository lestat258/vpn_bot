# VPN4US — приёмочные испытания и переход с YadrenoVPN

Статус: **QA / подготовка**, не разрешение на запуск для клиентов.

## Основное правило безопасности

- Действующий YadrenoVPN, его клиенты и панель 3x-ui остаются неизменными во время разработки.
- Проверки с реальными платежами, продлением, удалением и записью в общую 3x-ui запрещены до отдельных тестовых реквизитов и изолированной БД.
- У нового Telegram-бота должен быть **отдельный токен**, тестовые аккаунты и тестовая БД. Никогда не менять токен существующего бота ради теста.
- Не применять обновление в `/opt/vpn-bot` или `systemctl start vpn-bot`, пока тестовый контур не готов и его сетевые записи не ограничены.

## Выявленные проблемы, исправленные в рабочей ветке

1. Отсутствовали обработчики части публичных команд (/profile, /buy, /install, /faq, /help, /referral, /admin).
2. Кнопка статистики защиты от спама не имела callback-обработчика, а обработчик настроек дублировался.
3. Некорректно обрабатывались неизвестные текстовые сообщения и устаревшие inline-кнопки.
4. В /start реферальная запись создавалась через второе SQLite-соединение до завершения первой транзакции; уведомления ссылались на неверную переменную.
5. При оплате использовался возврат в посторонний Telegram-бот вместо текущего аккаунта.
6. Инструкция по подключению могла реконструировать URL из случайного сервера вместо сохранённой ссылки.
7. Чувствительные 2FA-пути были признаны публичными; новая база содержала пароль admin/admin.
8. Старые кнопки удаления ключей могли выбирать неправильный сервер и стирать запись SQLite после неудачного удаления. На время QA удаление **намеренно заблокировано** с понятным ответом пользователю.

## Открытые критические блокеры перед реальными клиентами

- Продление через `services/vpn_service.py` и `auto_renew.py` всё ещё выбирает сервер по текущей нагрузке, а не по доказанному `subscriptions.server_id`. Требуется ownership-guard и подтверждение 3x-ui ДО корректировки даты/баланса.
- Сценарий «Купить второй ключ» конфликтует с защитой журнала выдачи, запрещающей вторую активную подписку у того же пользователя. Уточнить продуктовую политику и согласовать UI с серверным правилом.
- Заменить временный запрет удаления на удаление только подтверждённых vpn4us-клиентов на конкретных согласованных inbound, с проверкой UUID/SubID и безопасным восстановлением.
- Админ-авторизация: защита от CSRF для изменяющих форм и API, надёжное хранение хэша пароля, повторная аутентификация на особо опасные операции, безопасные сессии и логирование.
- Тестовая среда пока не изолирована от боевой по БД, токену Telegram и API; до её появления полноценное взаимодействие в Telegram/веб-админке НЕ считается протестированным.
- Ручная проверка статуса внешних платёжных шлюзов, callback webhook, идемпотентности и проверки фактической выдачи подписки после оплаты.

## Приёмочные сценарии Telegram

| Действие | Ожидаемый результат |
| --- | --- |
| /start новым пользователем | Приветствие, регистрация, понятная кнопка меню |
| /start повторно | Без дублирования учётки, сохранение подписок |
| /menu, /help, /profile, /buy, /install, /faq, /referral | Каждая команда даёт ожидаемое сообщение |
| Все reply/inline-кнопки и «Назад» | Нет молчащих кнопок, понятная навигация |
| Установка на Android/iOS/Windows | Только собственная сохранённая HTTPS-ссылка |
| Установка без активной подписки | Понятное предложение выбрать тариф |
| Пробный период | Только один раз, с проверкой выдачи на выбранных inbound |
| Второй ключ при активной подписке | Согласованный продуктовый сценарий без ложных обещаний |
| Оплата | Верная цена, успешный возврат в **текущий** бот |
| Повтор webhook | Без повторной выдачи, списания или потери подписки |
| Продление и авто-продление | Только собственная подписка, точный сервер и атомарность операций |
| Недоступность API 3x-ui | Нет повторной выдачи, корректное сообщение и журнал инцидента |
| Реферальная ссылка и промокоды | Корректная регистрация, бонус и сообщение |
| Просроченные/старые сообщения | Ошибка с возможностью вернуться в меню |
| Удаление | Пока заблокировано; после реализации — только подтверждённый клиент vpn4us |

## Приёмочные сценарии веб-админки

- Вход без пароля / с неправильным паролем — отказ; 2FA QR и статус без авторизации недоступны.
- Все пункты бокового меню открываются, формы валидируются, ссылки и «Назад» работают.
- Настройки, тарифы, пользователи и промокоды меняются только в тестовой БД.
- Управление серверами не затрагивает действующую панель и клиентов.
- Восстановление резервных копий, удаление, массовая рассылка и реальные платежи отключены в QA до целевых проверок.
- Проверить мобильную вёрстку, сообщения об ошибках, сохранение данных и повторную загрузку страниц.

## План перехода с YadrenoVPN

1. Завершить QA на отдельном тестовом Telegram-боте, отдельной БД и тестовом API 3x-ui (или строгих моках).
2. Подготовить резервные копии и сверку существующих подписок: telegram_id, срок, сервер, клиентский UUID/SubID, inbound, ссылка и оплата. Секреты в отчёт не выводить.
3. Выбрать вариант перехода: **бережная передача существующих доступов** или выдача новых доступов. По умолчанию не перевыпускать и не удалять работающие ключи.
4. Небольшая контрольная группа добровольцев, затем ограниченные партии пользователей с уведомлениями и работающей поддержкой.
5. До окончания срока действующих подписок сохранять доступ в старом сервисе. Никаких массовых удалений и автоматических записей в общую панель.
6. Проверить механизмы отката: восстановление бота, настроек и маршрутизации сообщений без потери платёжного журнала и клиентских доступов.
7. Переход на широкий запуск — только после подписанного чек-листа и оценки оставшихся рисков.

## Текущие автоматические проверки

- `source-checks.yml`: исходники, секреты, компиляция, платёжные smoke-тесты.
- `vpn-regressions.yml`: политики inbound, защита выдачи/журнала, безопасное развёртывание.
- `test_ui_wiring.py`: наличие обработчиков для reply- и inline-кнопок, а также публичных команд.

Все проверки CI — **не замена** испытаний живого Telegram API, платёжного sandbox, веб-интерфейса и 3x-ui.
